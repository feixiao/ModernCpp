# 现代 C++ 快速入门

本仓库收集了 275 个现代 C++ 示例文件，内容覆盖 C++11、C++14、C++17 和 C++20。示例按章节放在 [`src`](src) 目录中，适合围绕单个语言特性阅读、修改和验证。

参考资料：[《Modern C++ Tutorial: C++11/14/17/20》](https://github.com/changkun/modern-cpp-tutorial.git)

学习每个特性时，不只看“语法怎么写”，还要回答三个问题：**它解决什么问题、什么时候适合用、相较原有写法有什么具体好处**。下面的章节索引按这三个维度组织，并保留源码入口。

## 目录结构

```text
.
├── CMakeLists.txt       # 7 个早期示例的构建入口
├── ReadMe.md            # 项目说明和源码导航
└── src/
    ├── 1-1.cpp
    ├── 2-1.cpp
    ├── 2-2.cpp
    └── ...              # 共 42 章、275 个示例
```

`src/<章节>-<序号>.cpp` 是统一命名规则。例如，`6-1.cpp` 到 `6-9.cpp` 都属于第 6 章，主题是移动语义和完美转发。同一章通常通过一组相近代码展示正确写法、错误写法及版本差异。

## 5 分钟熟悉 `src`

1. 从下方章节索引定位感兴趣的语言特性。
2. 先读该章的语法作用和使用场景，再打开源码入口，识别 `main()`、核心类型和关键表达式。
3. 按编号比较同章示例：原有写法有什么成本，新特性减少了哪些重复、错误或资源开销？
4. 单独编译并运行一个示例，不要直接假设整章都能批量构建。
5. 修改输入、类型或限定符，再观察编译结果和输出。

以下命令适合快速查看和比较一章代码：

```bash
# 列出第 6 章全部示例
printf '%s\n' src/6-*.cpp

# 查找第 41 章中的 Concepts 和约束表达式
rg -n 'concept|requires' src/41-*.cpp

# 比较两个相邻示例
diff -u src/21-1.cpp src/21-2.cpp
```

## 把语法放回使用场景

下面三组对照展示如何从“会写”进一步判断“为什么用”。

### 结构化绑定：接收多个返回值

场景：函数同时返回两个坐标，调用者需要分别命名并使用它们。

- 原有写法：[20-1.cpp](src/20-1.cpp) 使用 C++11 的 `tuple`，先声明 `int x, y`，再用 `std::tie(x, y)` 接收结果。
- 新写法：[20-2.cpp](src/20-2.cpp) 用 C++17 的 `auto [x, y] = return_multiple_values();` 同时完成声明、类型推导与分解。
- 好处：不用重复声明元素类型，也不用在后续代码中用 `get<0>`、`get<1>` 表示含义；主要收益是可读性，不应宣称必然更快。
- 边界：结构化绑定会引入新名称；给已有变量赋值时，`std::tie` 仍适用。分解已有对象时，`auto [x, y] = obj` 通常会复制对象，需共享或修改原对象时应考虑引用形式。

### 移动语义：转移大对象的资源

场景：把一个不再需要的大缓冲区交给另一个对象。如果执行深拷贝，需要新分配内存并复制数据；类型提供移动操作后，可以转交资源所有权。

- 语法作用：`std::move(obj)` 把表达式转换为可参与移动重载选择的形式，真正转移资源的是被选中的移动构造或移动赋值函数。
- 好处：[6-5.cpp](src/6-5.cpp) 的移动构造只接管指针并清空源指针，相比其复制构造中的分配与 `memcpy`，可避免复制整个缓冲区。这个收益以允许转移所有权为前提。
- 边界：同一文件的 `get_pool(const BigMemoryPool& pool)` 中，`std::move(pool)` 得到的是 `const` 右值，不能绑定到通常的 `BigMemoryPool&&` 移动构造参数，因此这里仍会调用复制构造。不能仅凭出现 `std::move` 就认定消除了拷贝。
- 使用判断：仍需保留独立副本时应复制；只需只读访问时可传 `const&`。移动后源对象的可用操作取决于类型契约，不能假设值保持不变或一定为空。

### Concepts：把模板要求写进接口

场景：模板只接受整数类型，希望调用处就能看清限制，并在传入不符合要求的类型时得到约束诊断。

- 原有写法：[41-1.cpp](src/41-1.cpp) 用 `enable_if_t` 配合 `is_integral_v` 表达限制，把要求放进默认模板参数；这种机制源自 C++11，其中的 `_t`、`_v` 简写分别需要 C++14、C++17。
- 新写法：[41-2.cpp](src/41-2.cpp) 在 C++20 中定义 `IntegerType` 概念，再用 `template <IntegerType T>` 直接约束参数。
- 好处：约束有名称、可复用，接口更容易理解；不满足要求时，编译器通常能直接指出失败的约束。两者都是编译期机制，收益主要是接口表达和维护性。
- 边界：约束只能验证写出的类型或表达式要求，不能证明业务正确性，例如一个比较器是否真的满足严格弱序；仍需实现者保证语义。

## 编译和运行

### 使用 CMake 构建已配置示例

根目录的 `CMakeLists.txt` 使用 C++17，目前只配置了 7 个目标：

| 目标 | 源文件 |
|---|---|
| `ex01` | `src/1-1.cpp` |
| `ex02-01` | `src/2-1.cpp` |
| `ex02-02` | `src/2-2.cpp` |
| `ex03` | `src/3-1.cpp` |
| `ex04` | `src/4-1.cpp` |
| `ex06_05` | `src/6-5.cpp` |
| `ex06_08` | `src/6-8.cpp` |

必须使用独立构建目录；项目会拒绝在源码目录内构建：

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build --target ex01
./build/ex01
```

当前 CMake 配置只处理 Linux 和 macOS。

### 单独编译任意示例

学习 `src` 时，推荐直接编译单个文件。C++20 可以覆盖多数示例使用的语言特性：

```bash
mkdir -p build/single
c++ -std=c++20 -Wall -Wextra src/29-2.cpp -o build/single/29-2
./build/single/29-2
```

涉及线程的示例通常还需要 `-pthread`：

```bash
c++ -std=c++20 -pthread src/25-3.cpp -o build/single/25-3
./build/single/25-3
```

## 阅读时的注意事项

- 一些示例故意展示编译失败，例如错误的 `override`、失败的 `static_assert` 或不满足 Concepts 的类型。源码注释通常会标出“编译失败”或“编译错误”。
- 一些文件是代码片段，不包含完整的头文件或 `main()`；它们用于解释语法，不是独立程序。
- 少数示例依赖编译器扩展、平台相关汇编或早期 `<experimental/...>` 头文件，现代编译器不一定继续提供对应接口。
- 部分文件在注释中保留了汇编或 GIMPLE 输出，用于观察语言特性对生成代码的影响。
- 遇到失败时，先判断它是教学反例、标准版本差异，还是平台/编译器扩展差异，再决定是否修改代码。
